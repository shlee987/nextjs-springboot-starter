# 변경과 검증

## 규칙

- 요청한 동작에 필요한 파일만 수정한다. 무관한 포맷 변경·이름 변경·리팩터링은 섞지 않는다.
- 변경 전에 대상 구현과 영향을 받는 호출부·타입·테스트를 확인한다. 파일·심볼·경로를 좁혀 탐색하고 근거가 있을 때만 범위를 넓힌다. 이미 확인한 정보는 관련 변경·새 증거·문맥 소실이 없으면 재사용한다.
- 프로젝트의 기존 기능·의존성으로 해결할 수 있는지 확인한 후 새 의존성을 고려한다.
- 자동 생성 코드·컴파일된 CSS·빌드 산출물은 직접 수정하지 않고 원본·템플릿·생성 설정을 수정한다. 갱신이 필요하면 기존 생성 절차를 사용하고, 저장소가 생성 결과를 관리하는 경우 관련 결과도 함께 반영한다.
- 코드·테스트·스크립트에 개발자 PC의 절대 경로를 하드코딩하지 않는다. 프로젝트 기준 경로·설정·기존 임시 디렉터리 방식을 사용하고 외부 경로는 실행 환경에서 주입한다.
- 언어·런타임·프레임워크·라이브러리·스타일 도구의 버전과 지원 범위는 대상 모듈의 설정·잠금 파일·기존 실행 환경을 기준으로 확인하고 재사용한다. 최신 예제의 문법·API·옵션을 그대로 적용하지 않으며, 호환성이 불명확할 때만 해당 버전의 타입·구현·공식 문서를 확인한다.
- 변경한 부분에서 발생한 버전 호환성·deprecated·타입·설정 경고는 지원되는 방식으로 해결한다. 경고를 숨기거나 불필요한 버전 업그레이드로 우회하지 않는다. 기존 경고나 해결에 별도 업그레이드·범위 확대가 필요한 경고는 원인과 필요한 조치를 알리고 무관한 수정으로 확대하지 않는다.
- 검사 명령은 실제 프로젝트 설정에서 확인한다. 특정 패키지 매니저나 명령이 있다고 가정하지 않는다.
- 타입·시그니처 변경은 관련 타입 검사·컴파일을, 동작 변경은 해당 동작의 테스트를 우선한다.
- 포맷만 변경하면 기존 formatter의 대상 파일 검사로 확인한다. 문서만 변경하면 내용·경로를 확인한다.
- 여러 모듈에 영향을 주거나 좁은 검사로 영향 범위를 확인할 수 없으면 검사 범위를 넓힌다.
- 검사를 통과시키기 위해 검증 조건을 약화하지 않는다. 기존 실패와 변경으로 생긴 실패를 구분한다.
- 완료 전에 변경 부분의 규칙 위반을 직접 수정한다. 실제 실행한 검사와 실행하지 못한 검사를 구분해서 보고한다.
- 함수 주석은 존재 여부만 확인하지 않는다. `comments.md`에 따라 주석만 읽어도 중요한 데이터 출처·핵심 처리·결과·부수 효과·실패 계약을 이해할 수 있는지 실제 구현과 대조한다.
- 파일·데이터 변경은 `design.md`의 부분 실패 기준에 따라 기존 데이터 손상, 일부 반영, 동기화 삭제의 조회 완전성을 확인한다. 동작 변경 시 해당 위험에 맞는 실패 검증을 수행하되 관련 없는 전체 복구 체계나 중복 테스트를 추가하지 않는다.

## 검증 범위

- 긴 빌드·테스트·실행 로그는 파일에 보관하고 종료 코드·관련 성공 요약·필요한 오류 부분만 확인·출력한다. 실패는 관련 문맥을 충분히 확인해 원인을 파악하고, 로그·요약에 비밀정보를 노출하지 않는다. 출력이 짧은 명령까지 파일 저장을 강제하지 않는다.

- 주석·문서는 내용과 참조 경로, 형식 변경은 기존 formatter, 타입·시그니처는 관련 타입 검사·컴파일, 동작 변경은 해당 테스트부터 확인한다.
- 공통 코드·의존성·빌드 설정 변경이나 좁은 검사로 영향을 확인할 수 없는 경우 관련 모듈 검사 또는 전체 빌드·테스트로 확대한다. 프로젝트가 요구하는 필수 검사는 생략하지 않는다.
- 같은 코드·환경에서 통과한 검사는 새 변경·실패·미확인 영향이 없으면 반복하지 않는다.
- 검증 도구가 없으면 가능한 코드·호출 계약 확인을 수행하고 한계를 알린다. 작은 변경의 검증만을 위해 새 도구를 설치하지 않는다.

## 테스트

- 기존 테스트를 우선 활용하고, 실제 업무 동작·실패·회귀를 지속적으로 보호할 필요가 있을 때만 테스트를 추가하거나 갱신한다. 단순 주석·형식 변경에 테스트를 추가하지 않는다.
- 단순 접근자·상수·전달·프레임워크 동작·private 구현 구조만 확인하거나 커버리지 수치만 높이는 테스트는 만들지 않는다. 해당 동작 자체가 실제 외부 계약이면 필요한 검증을 유지한다. 같은 동작을 중복 검증하는 테스트·파일을 늘리지 않는다.
- 기존 테스트 도구와 구조를 사용한다. 구현을 그대로 복제하거나 private 함수 호출만 확인하는 테스트 대신 입력과 관찰 가능한 결과·실패를 확인한다.
- 테스트는 준비·실행·검증을 구분하고, 이름에 대상 동작·조건·기대 결과를 드러낸다. 정상·주요 경계·의도한 실패 중 변경에 해당하는 사례를 다룬다.
- DB를 사용하는 검사·테스트는 실행 전에 `database-access.md`의 승인 기준을 적용한다.
