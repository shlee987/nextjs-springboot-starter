# 책임과 흐름

## 규칙

- 현재 요구사항을 만족하는 구조를 만든다. 예상되는 미래 재사용만으로 계층·확장 지점·설정을 추가하지 않는다.
- 새 구현 전에 표준 라이브러리와 관련 모듈의 기존 구현을 확인한다. 입력·반환값·실패 처리·부수 효과가 필요한 동작과 맞으면 재사용한다.
- 같은 기능의 별도 경로를 옆에 추가하기보다 기존 책임 소유자의 구현을 수정한다. 병렬 구현은 실제로 다른 계약·호환성 요구가 있을 때만 유지하고, 대체한 작업 범위의 이전 경로는 사용처·계약을 확인해 정리한다.
- 기능의 계약에 맞는 기존 모델을 우선 활용한다. 새 모델은 역할·재사용의 이점이 있을 때만 만들고, 단순 입력은 개별 파라미터로 전달한다.
- 함수는 호출 횟수보다 성격에 따라 배치한다. 범용 계산·변환은 공통 유틸리티, 업무 규칙은 해당 업무 모듈, 내부 상태·구현에 의존하는 보조 처리는 클래스·컴포넌트 내부에 둔다. 외부 연동과 화면 이벤트 처리를 범용 유틸리티에 섞지 않는다.
- 함수 분리는 현재 중복 제거, 복잡한 계산·조건의 의미 표현, 서로 다른 책임의 경계 중 하나를 개선할 때 한다.
- 한 번만 호출되는 함수도 위 기준을 만족하면 허용한다. 호출 횟수만으로 분리·병합하지 않는다.
- 코드가 비슷하다는 이유만으로 합치지 않는다. 책임과 변경 이유가 같으면 공통화하며, 이름·인자로 동작이 명확한 작은 분기는 허용한다. 서로 다른 책임을 합쳐 호출부나 내부 흐름이 불명확해지면 분리한다.
- 다른 함수를 그대로 호출할 뿐인 중간 함수는 만들지 않는다. 인터페이스 구현이나 외부 연동 경계 등 실제 계약이 있으면 허용한다.
- 함수 길이를 줄이거나 테스트용 호출 경로를 만들기 위한 목적만으로 함수를 분리하지 않는다.
- 테스트 편의만으로 제품 코드의 공개 범위를 넓히거나 final을 제거하거나 생성자·인터페이스·보조 클래스를 추가하지 않는다. 실제 제품 동작·계약에 필요한 구조 변경은 허용한다.
- 조회·계산 함수 안에 저장·삭제 등 이름에서 예상할 수 없는 변경 동작을 넣지 않는다.
- 입력 오류·처리 불가 조건은 앞에서 반환하거나 예외로 처리해 정상 흐름의 중첩을 줄인다. 뒤에서는 이미 확인한 조건을 반복 검사하지 않는다. 상태 변경·새 외부 결과로 전제가 달라지면 다시 검사한다.
- 방어 검증·복사·래퍼·재시도·대체 동작은 실제 호출 계약·외부 실패·상태 소유권·보안·신뢰성 요구에 근거할 때만 추가한다. 이미 보장된 내부 조건이나 불가능한 상황을 대비해 흐름을 복잡하게 만들지 않는다.
- 이번 변경 범위에서 여러 함수로 이동해야만 핵심 흐름을 알 수 있고 중간 함수에 별도 책임이 없으면 합친다. 무관한 기존 구조까지 정리하지 않는다.
- 기존 공개 계약, 실제 여러 사용처, 보안·신뢰성 요구를 단순화 명목으로 제거하지 않는다.
- 클래스·모듈에는 같은 책임에 속하는 처리와 상태·의존성을 묶는다. 독립된 업무나 외부 연동 책임이 섞이면 분리한다. 파일 길이·메서드 수만으로 나누지 않는다.

## 데이터 변경과 부분 실패

- 파일·데이터를 덮어쓸 때 중간 실패로 기존 정상 데이터가 잘리거나 손상될 수 있는지 확인한다. 보존이 필요한 경우 임시 저장 후 교체 등 대상 저장소와 실행 환경에서 지원하는 안전한 반영 방식을 사용한다.
- 여러 파일·데이터를 변경할 때 전체 성공이 필요한지, 일부 성공을 허용하는지 요구사항과 실패 영향으로 판단한다. 일부 반영을 허용하면 실패 후 상태와 재실행·복구 방법을 명확히 한다. 재실행이 안전한지는 실제 동작으로 확인한다.
- 항상 전체 트랜잭션·백업·롤백 체계를 만들지는 않는다. 단일 파일의 안전한 교체와 여러 대상 전체의 원자성을 구분하고, 허용되는 실패 상태에 맞는 최소한의 보호를 적용한다.
- 조회 결과에 없다는 이유로 기존 파일·데이터를 삭제하는 동기화는 조회 범위·권한·완전성을 확인한다. 조회 실패·권한 부족·부분 조회를 정상적인 삭제 근거로 취급하지 않는다. 정상적인 빈 결과까지 일괄 오류로 막지는 않는다.
- 호출자가 알아야 하는 부수 효과와 실패 계약의 주석 작성 기준은 `comments.md`를 따른다.

## 선택 정책: 인터페이스와 구현 분리

- 기본값: 인터페이스·구현 클래스를 일괄 생성하지 않는다. 현재 구현 교체, 외부 연동 경계, 공개 계약이 필요할 때 도입한다. 테스트의 mock 사용만을 이유로 생성하지 않는다.
- 관리자가 특정 계층의 인터페이스·구현 분리를 필수로 정하면 프로젝트에 명시된 해당 정책을 우선한다.
- 이 선택을 적용하기 위해 무관한 기존 인터페이스를 삭제하거나 구조를 변경하지 않는다.

## 분리 예시

### 별도 책임이 없는 중간 함수

```java
// 불필요한 중간 단계
void saveOrder(Order order) {
    executeSave(order);
}

private void executeSave(Order order) {
    orderRepository.save(order);
}

// 개선: 중간 함수에 별도 책임이 없으면 직접 호출
void saveOrder(Order order) {
    orderRepository.save(order);
}
```

인터페이스 구현이나 외부 연동 경계를 담당하는 경우에는 단순 전달도 허용한다.
위 코드는 전후 비교이며 두 saveOrder를 함께 선언하는 템플릿이 아니다.

### 한 번만 호출해도 의미를 드러내는 함수

```java
if (canCancel(order)) {
    order.cancel();
}

private boolean canCancel(Order order) {
    return order.isPending() && !order.isShipmentStarted();
}
```

canCancel은 취소 조건의 의미를 드러내므로 한 번만 호출해도 분리할 수 있다.
업무 정책에 의존하므로 해당 업무 모듈에 두고, 상태를 변경하지 않는다는 이유만으로 공통 유틸리티에 옮기지 않는다.
