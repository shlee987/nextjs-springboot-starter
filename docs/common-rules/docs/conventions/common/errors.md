# 오류 처리 책임

## 규칙

- 명시적으로 무시·복구하도록 정한 경우 외에는 실패를 호출자 또는 오류 처리 경계에 전달한다. 빈 catch, 성공 값, 근거 없는 기본값으로 실패를 숨기지 않는다. 자동 재시도·대체 동작을 임의로 추가하지 않는다.
- 오류 처리 변경 전 관련 예외 클래스와 처리기를 확인한다. 실제 사용처·처리 경로로 프로젝트의 오류 체계를 식별하고, 클래스 이름만으로 공통 여부를 판단하지 않는다. 이미 확인한 체계는 변경되지 않으면 다시 탐색하지 않는다.
- 업무 오류는 기존 오류 체계의 해당 예외 클래스·오류 정의를 사용한다. 개별 코드에서 별도의 응답 형식·메시지 변환·동일 역할의 예외 클래스를 만들지 않는다.
- catch는 복구, 의미 있는 예외 변환, 최종 응답 처리가 필요한 위치에만 둔다. 표준·라이브러리 예외를 모든 호출 단계에서 감싸지 않는다. 처리 없이 그대로 재던지는 catch는 만들지 않는다.
- 사용자 응답과 표시 메시지의 변환은 기존 공통 처리 경계에 모은다. 개별 함수에서 이를 우회해 예외 원문을 반환하거나 표시하지 않는다. 메시지·오류 코드 형식은 프로젝트의 정의를 따른다.
- 예상하지 못한 예외도 최종 경계에서 안전한 실패 응답으로 처리한다. 예외 원문·스택·SQL·경로 등 내부 진단 정보를 사용자에게 노출하지 않고, 정제된 메시지 또는 안전한 기본 오류 메시지를 사용한다.
- 서버의 원인·스택과 필요한 진단 문맥은 로그에 보존하되 비밀정보는 제외한다. 같은 실패를 여러 계층에서 기록하고 재던지지 않는다. 최종 처리·기록 책임이 있는 경계에서 기록하고, 예외 변환 시 원인을 보존한다.
- 실제 입력·외부 시스템·호출 계약에서 발생 가능한 실패를 처리한다. 방어 코드의 도입 기준은 `design.md`를 따르며 근거 없는 실패 시나리오를 추가하지 않는다.
- 기존 처리 체계가 없거나 여러 체계의 적용 범위가 불명확하면, 새 공통 체계를 임의로 추가하지 않고 필요한 기본 경계를 먼저 확인한다.

## Java·React 적용

- Java는 기존 Exception Handler와 예외 정의를 사용한다. 업무 코드에서 오류를 발생·전달하고, 공통 처리 경계에서 사용자 응답으로 변환한다.
- React의 API 요청 실패는 기존 공통 요청 클라이언트·인터셉터의 처리 경로를 사용한다. 메시지 변환·알림을 중복하지 않되, 작업별 복구·화면 상태 처리는 해당 호출부에서 수행할 수 있다.
- React 렌더링 오류는 기존 Error Boundary 경로를 사용한다. 이벤트·비동기 작업의 오류까지 Error Boundary나 인터셉터가 모두 처리한다고 가정하지 않고, 해당 경로의 오류를 실제 처리 가능한 경계에 전달한다.
