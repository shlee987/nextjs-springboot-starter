# 주석

## 규칙

- 주석은 한국어로 작성한다. API·타입·식별자·기술 용어는 원문을 유지한다. 프로젝트에 명시된 언어 정책이 있으면 우선한다.
- 작성·수정하는 각 함수의 선언 바로 위에 Java는 Javadoc, JS/TS는 JSDoc/TSDoc 형식의 문서 주석을 둔다. 공개 여부와 관계없이 함수의 역할을 짧게 설명해 IDE에서 확인할 수 있게 한다.
- 함수 설명은 이름을 그대로 번역하지 않고 수행 목적과 결과를 적는다. 데이터 출처(DB·외부 API·파일·입력 등), 핵심 처리, 반환값 또는 생성 결과 중 함수 이해에 중요한 내용을 포함한다. 다른 함수에 위임하더라도 호출자가 알아야 하는 핵심 동작은 생략하지 않는다.
- 파일·데이터 생성·덮어쓰기·삭제 등 주요 부수 효과와 호출자가 알아야 하는 실패 동작을 설명한다. 부분 실패 후 변경이 남거나 실패를 기록하고 계속하는 계약이 중요하면 명시한다. 실제 구현에서 보장하지 않는 원자성·복구를 약속하지 않는다.
- 내부 호출 순서·변수명·구현 세부를 나열하지 않고 계약 수준으로 설명한다. 단순한 함수에 모든 항목을 억지로 채우거나 태그·장문 설명을 반복하지 않는다. 인라인 콜백은 문서 주석을 붙이기 위해 별도 함수로 추출하지 않는다.
- 매개변수·반환값·예외에는 단위, 허용값, 값 없음, 실패 조건 등 호출자가 알아야 할 정보를 적는다. 이름·타입만 반복하는 태그를 기계적으로 채우지 않는다.
- 함수 내부에는 유효성 확인, 데이터 가공, 저장, 결과 구성 등 실제 주요 처리 구간의 시작에 짧은 주석을 둔다. 단계가 바뀌는 위치를 드러내며, 정해진 단계를 억지로 만들거나 짧고 단일한 처리에 구간 주석을 반복하지 않는다.
- 개별 코드 줄의 자명한 대입·호출·반복 동작은 설명하지 않는다. 의미가 파악하기 어려운 로직, 보편적이지 않은 처리, 업무 조건, 외부 제약·계약, 우회 이유는 해당 코드 가까이에 설명한다.
- 설명이 필요한 원인이 모호한 이름이나 불필요한 복잡도라면 먼저 코드를 명확하게 만든다.
- 기존 소스·쿼리 주석은 의도·배경·제약을 확인하고 보존한다. 새 주석 작성 기준을 기존 주석의 일괄 삭제·축약·재작성 근거로 사용하지 않는다. 이번 변경으로 설명이 달라진 부분만 갱신하고 여전히 유효한 이유·주의사항은 유지한다. 주석은 관련 코드·조건의 제거 또는 설명이 더 이상 유효하지 않음을 확인한 경우에만 제거하며, 의미가 불명확하면 추측해 덮어쓰지 않는다.
- 코드·쿼리를 이동하거나 분리할 때 관련 주석도 의미가 연결되는 위치로 옮긴다. 완료 전 변경 diff에서 기존 주석의 누락과 변경 동작에 맞지 않는 설명을 확인한다.
- 사용하지 않는 코드의 보관 목적으로 주석 처리된 구현을 추가하지 않는다.
- TODO에는 남은 작업을 구체적으로 적고, 임시 우회에는 이유와 알려진 제거 조건을 적는다. 알 수 없는 담당자·일정·조건은 지어내지 않는다.

## 예시

아래는 주요 구간을 보여주는 Java 설명용 골격이며, `...`은 실제 코드가 아니다.

```java
/**
 * 요청 내용을 검증하고 주문을 생성한다.
 */
public OrderResult createOrder(CreateOrderRequest request) {
    // 입력값과 주문 가능 조건 확인
    ...

    // 저장할 주문 데이터 구성
    ...

    // 주문 저장
    ...

    // 생성 결과 구성
    ...
}
```

## 문서 주석과 헤더

- Java 문서 주석 표기는 `../java/style.md`, JS/TS는 `../react/style.md`를 따른다.
- 새 파일의 타입·컴포넌트·모듈 역할을 짧게 설명한다. 기본값으로 작성자·작성일·수정 이력 헤더는 추가하지 않는다. 이력은 버전 관리에 맡기며 프로젝트가 요구하는 헤더·라이선스는 유지한다.
