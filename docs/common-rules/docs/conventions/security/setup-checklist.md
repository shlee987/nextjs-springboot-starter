# 초기 보안 설정 체크리스트

AI는 아래 항목을 프로젝트 구조에 맞게 검토한다. 해당하지 않는 항목은 이유를 기록한다. 모든 프로젝트에 동일한 설정값을 복사하지 않는다.

## 1. 착수와 설계

- 기술·버전·지원 기간, 데이터 민감도, 사용자 역할, 신뢰 경계, 외부 연동, 서비스별 공개 범위를 확인한다.
- ASVS 요구사항과 검증 수준을 정하고 인증·권한·데이터 흐름을 설계한다.
- 보안 정책과 호환되는 라이브러리를 선택한다. 특히 HTML 편집기·외부 스크립트·동적 코드 실행·인라인 스크립트 요구를 미리 확인한다.
- 로컬·개발·운영 설정과 시크릿 공급 방법을 구분한다.

## 2. 프런트엔드

- 비밀값과 민감한 서버 데이터가 브라우저 번들·소스맵·로그에 포함되지 않도록 경계를 설정한다.
- 출력은 문맥에 맞게 처리하고 HTML 직접 삽입은 필요성을 제한하며 허용 목록 기반 정화를 적용한다. 입력 전체의 일괄 문자열 치환으로 대체하지 않는다.
- CSP는 실제 리소스·API·WebSocket·iframe·폼 전송에 맞게 설계한다. 개발용 eval 허용 등이 운영 정책에 섞이지 않게 한다.
- nonce·hash 등 제한적인 스크립트 실행 정책을 검토한다. unsafe-inline·unsafe-eval이 필수인 의존성은 도입 단계에서 대안과 영향을 검토한다.
- 허용 출처는 스킴·호스트·포트·하위 도메인 범위를 확인한다. 와일드카드로 포트까지 자동 허용된다고 가정하지 않는다.
- 쿠키·캐시·보안 헤더와 인증 후 화면의 데이터 노출을 확인한다.

## 3. 백엔드·API·배치

- 인증과 자원별 권한을 서버에서 검증한다. 사용자·조직·테넌트별 접근 경계를 확인한다.
- 입력 형식·크기·범위를 검증하고 SQL은 바인딩한다. 파일 경로·명령 실행·외부 URL 요청은 별도로 제한한다.
- 인증 방식에 따라 CSRF·CORS·세션·토큰 저장 및 만료·로그아웃·속도 제한을 설계한다.
- 운영 오류에 스택·쿼리·키·내부 구조가 노출되지 않게 하고 로그에서 비밀번호·토큰·개인정보를 제외한다.
- 파일 업로드는 크기·유형·저장 위치·실행 가능성·다운로드 권한을 검증한다.
- 시크릿은 외부에서 주입하고 배포 환경에서 누락·빈값이면 안전하게 시작 실패하도록 한다. 저장 암호화와 키 관리를 분리한다.
- 배치도 API와 동일하게 시크릿·최소 권한·로그 보호를 적용하고 실행 계정·재실행·중복 실행·실패 처리 기준을 정한다.

## 4. DB·서버·클라우드

- 애플리케이션·마이그레이션·관리 계정을 구분하고 DB 및 실행 계정 권한을 최소화한다.
- 네트워크 접근을 제한하고 전송·저장 암호화, 백업 보호 및 복구 검증을 설계한다.
- OS·웹 서버·DB·클라우드 서비스는 실제 버전에 맞는 공식 지침과 CIS 기준으로 구성한다.
- TLS 종료 위치, 인증서 갱신, 프록시 신뢰 설정, HTTP 필요 구간을 확인한다.
- HSTS·HTTPS 리디렉션·하위 도메인 적용은 실제 통신과 인증서 구성에 맞춰 결정하고 검사한다.
- 불필요한 서비스·관리 포트·디버그 화면·기본 계정·디렉터리 목록·버전 노출을 제한한다.
- 서비스 계정, 관리자 MFA, 패치, 감사 로그, 경보, 백업과 복구를 운영 기준에 포함한다.

## 5. CI/CD·공급망

- 저장소 변경 권한·보호 브랜치·리뷰·파이프라인 정의 변경 권한을 통제한다.
- 신뢰하지 않는 PR·브랜치의 실행이 시크릿과 운영 배포 권한에 접근하지 못하게 한다.
- 빌드 실행 환경을 격리하고 개발·운영 권한을 분리한다. 가능한 환경에서는 단기 자격증명·워크로드 신원을 사용한다.
- 시크릿이 로그·명령행·캐시·산출물에 남지 않게 한다. 마스킹만으로 노출 방지를 완료했다고 판단하지 않는다.
- 의존성·액션·플러그인의 출처와 버전을 통제하고 업데이트 정책을 정한다.
- 비밀값 탐지·SAST·의존성 검사 및 필요한 IaC·컨테이너 검사·DAST를 단계에 배치하고 실패 기준을 정한다.
- 검증한 산출물을 배포하며 출처·무결성·보관 권한을 확인한다. 위험도에 따라 SBOM·서명·빌드 이력 증명을 적용한다.
- 동일 대상 동시 배포 충돌을 막고, 필요한 승인·감사·롤백·배포 후 정상 동작 및 보안 검증을 마련한다.

## 6. 완료 판단과 지속 관리

- 정상 기능과 함께 미인증·타 사용자·잘못된 입력·누락 시크릿·금지 출처 등 거부되어야 하는 동작도 확인한다.
- 실제 배포 응답의 헤더와 인증·권한을 검사한다. 설정 파일에 적혀 있다는 이유만으로 적용 완료로 판단하지 않는다.
- ZAP 같은 동적 검사와 소스·의존성·시크릿 검사를 함께 사용한다. 자동 검사 결과가 없다는 것만으로 안전을 보장하지 않는다.
- 빌드된 JS에서도 유효한 문제가 발견될 수 있다. 생성물은 원본 코드·의존성·빌드 설정·응답 정책에서 수정 가능한지 검토한다.
- 안내성 규칙·오탐은 근거를 확인해 최소 범위로 제외한다. 정보 등급 전체 또는 특정 디렉터리 전체를 일괄 제외하지 않는다.
- 수정 완료·오탐·위험 허용·보류를 구분하고 예외의 사유·범위·재검토 조건을 남긴다.
- 프로젝트 착수, 주요 업그레이드, 구조 변경, 보안 권고 발생 시 공식 문서를 재확인한다. 지침 갱신으로 필요한 변경을 검토하고 실제 검증 후 적용 기록을 갱신한다.
