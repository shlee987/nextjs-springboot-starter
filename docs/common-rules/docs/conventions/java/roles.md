# Java 역할 패턴

함수 분리·오류 처리 변경 시 부모 파일이 지정한 공통 문서를 적용한다.

## 메서드 역할

- JavaBeans 속성 접근자는 getX/setX를 사용한다. primitive boolean 속성은 isX를 사용할 수 있다.
- record의 접근자는 name() 같은 언어 기본 패턴을 유지한다. getName()을 추가하도록 강제하지 않는다.
- 판단 메서드는 is/has/contains 등 질문의 의미를 드러내고 boolean을 반환한다. JavaBeans 속성 규칙과 일반 판단 메서드를 혼동하지 않는다.
- 문자열 해석은 parseX, 다른 표현으로 변환은 toX, 계산은 calculateX처럼 동작을 드러낸다. 모든 함수에 이 접두사를 억지로 붙이지 않는다.
- 승인·취소 등 업무 동작은 approve/cancel 같은 구체적인 동사를 사용한다. 여러 업무 처리를 단순 속성 setter로 위장하지 않는다.
- 인터페이스 구현·오버라이드 메서드는 기존 계약의 이름과 동작을 유지한다.
- 인터페이스·구현 클래스 생성은 `../common/design.md`의 선택 정책을 따른다.

## 추천 조회·검증 계약

- 객체 속성의 get은 JavaBeans 계약을 따른다. 새 업무 조회 메서드는 조건 검색에 findX, 식별자·키 기반 조회에 getX, 대상의 존재가 필수인 조회에 getRequiredX를 사용한다. 기존 프레임워크·프로젝트 계약은 바꾸지 않는다.
- MyBatis SQL에 직접 연결하는 Mapper 메서드는 업무 조회 접두사 대신 `../sql/mybatis.md`의 Mapper 계약에 따라 SQL 동작을 표현한다. 이 예외를 적용할 때만 해당 문서를 읽는다.
- find 단건은 Optional 등 명시적인 값 없음 표현, 여러 건 조회는 빈 컬렉션을 기본으로 한다. get 단건은 null을 허용하고, getRequired는 대상이 없으면 기존 업무 오류 체계로 예외를 전달한다. 조회 자체의 실패를 null이나 빈 결과로 바꾸지 않는다.
- 예: findUserByEmail(email)은 조건 검색, getUser(userId)는 값 없음 허용 조회, getRequiredUser(userId)는 필수 조회다. 이름 구분만을 위해 같은 조회의 세 가지 메서드를 모두 만들지 않는다.
- is/has/can은 판단 결과를 반환한다. validate는 조건을 충족하지 못하면 기존 업무 오류 체계로 실패를 전달한다. 구조화된 검증 결과를 쓰는 프로젝트는 그 계약을 따른다.
- parse는 문자열 해석, from은 다른 표현에서 생성, of는 값 조합 생성의 기본 관례로 사용한다. 단순 생성에 불필요한 팩터리를 강제하지 않는다.

## 상태·공개 범위

- 내부 구현은 private, 외부 사용이 필요한 계약만 public으로 노출한다. 테스트만을 위해 공개 범위를 넓히지 않는다.
- 변경이 필요 없는 필드·의존성은 final을 기본으로 한다. 업무 상태 변경은 해당 상태를 소유한 객체·모듈에서 수행한다.
- null 허용 여부를 호출 계약에 드러낸다. Optional을 모든 필드·인자에 일괄 적용하지 않는다.
- 파일·스트림 등 AutoCloseable 자원은 try-with-resources로 닫는다. 소유권이 호출자에게 있으면 임의로 닫지 않는다.
- 프레임워크가 생성하는 객체·프록시·직렬화 계약은 해당 버전의 요구를 따른다.
