# Java 프레임워크 보충

해당 프레임워크를 사용하는 작업에만 적용한다. 라이브러리·버전·계층을 새로 도입하라는 지침이 아니다.

## Spring

- 웹 입력·응답은 Controller, 업무 동작은 업무 서비스·도메인, DB 접근은 기존 Repository/Mapper 경계에 둔다. 계층 이름만 맞추기 위한 전달 클래스를 만들지 않는다.
- 필수 의존성은 생성자 주입을 기본으로 한다. 서비스 인터페이스 생성 정책은 common/design.md를 따른다.
- 설정·상수·상태 값의 선택은 `../common/values.md`를 따른다. Spring Boot의 관련 설정 묶음은 @ConfigurationProperties를 우선하고 단일 값은 기존 주입 방식을 유지한다. 프로파일·환경 변수·외부 설정의 기존 우선순위를 따르며 사용하지 않는 설정 클래스를 만들지 않는다.
- 요청 검증은 기존 Bean Validation·업무 검증 방식을 사용한다. 웹 DTO와 영속 객체의 계약이 다르면 분리하고 내부 필드가 응답으로 노출되지 않게 한다.
- Controller 요청을 모델로 받을지 개별 파라미터로 받을지는 `../common/design.md`의 모델 선택 기준을 따른다.
- 함께 성공·실패해야 하는 DB 변경은 업무 경계의 트랜잭션으로 묶는다. private·self-invocation 등의 프록시 제약을 확인하고, 애너테이션만으로 동작한다고 가정하지 않는다.
- 오류 응답은 기존 Exception Handler를 사용한다. 응답 래퍼·상태 코드·오류 클래스를 별도로 복제하지 않는다.
- JPA/MyBatis 등은 실제 사용 중인 방식을 따른다. SQL은 값 바인딩을 사용하고, 외부 입력을 SQL 문자열로 직접 결합하지 않는다. 조회 변경 시 결과 매핑·불필요한 반복 조회를 확인한다.
- 프레임워크별 예약 애너테이션·생성 코드·프록시 계약은 실제 프로젝트 버전의 공식 문서를 필요한 경우에만 확인한다.
