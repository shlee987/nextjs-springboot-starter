# 재사용 가능한 Codex 개발 규칙

현재 상태: 추천 기본값으로 작성 완료한 재사용 규칙 세트. 실제 코드 생성 효과를 검증한 회사 표준은 아니다.

`AGENTS.md`는 AI용 진입점이며, 작업 조건에 따라 필요한 하위 문서를 선택한다.
공통 원칙, Java·React 역할·형식·문서화, SQL·MyBatis 규칙, UI 스타일 적용 규칙, 조건부 프레임워크 지침, 보안 초기 설정·검증 지침과 새 파일 템플릿을 포함한다.
일반 코딩에는 AGENTS.md와 조건에 맞는 규칙만 사용한다. 보안 작업에서는 security/guide.md를 통해 필요한 체크리스트 영역과 공식 URL만 선택한다. 이 README는 사용자 안내와 규칙 개정용이다.

## 다른 프로젝트에서 사용

이 폴더의 AGENTS.md와 docs/conventions, templates를 같은 상대 구조로 프로젝트에 복사한다.
기존 AGENTS.md가 있으면 덮어쓰지 않고 참조 조건과 규칙을 충돌 없이 통합한다.
공통 원본을 중앙에 두는 경우에는 대상 프로젝트의 진입점에서 실제 원본 경로와 읽는 조건을 명시한다.
이 폴더에 두었다는 이유만으로 다른 프로젝트나 현재 저장소 전체에 자동 적용되는 것은 아니다.

## 검토 순서

### 규칙 작성·개정 절차

이 절차는 이 규칙 세트를 작성·개정할 때만 적용한다. 다른 프로젝트의 일반 코딩 작업에 승인 절차를 추가하는 규칙이 아니다.

1. 한 번에 한 주제를 선정하고, 관련된 기존 AI 지침 사례의 실제 규칙을 분석한다. 이미 확인한 자료는 재사용하고 추가 확인이 필요한 내용만 조사한다.
2. 반복되는 원칙, 사례 간 차이, 공식 관례와 작성자의 선택을 구분한다. 출처와 추천 문안, 필요한 예외를 짧게 제시한다.
3. 기본 절차에서는 사용자가 결정할 사항과 제안 문안을 확인받은 뒤 수정한다. 사용자가 추천 기본값으로 일괄 완성을 요청한 범위는 중간 질문 없이 진행하고, 완료 후 선택한 기본값을 보고한다.
4. 사용자가 확정한 뒤 관련 문서와 참조를 수정한다. 이미 합의한 정책은 다시 묻지 않는다. 사용자가 명시적으로 바로 수정을 요청하면 해당 범위의 확정으로 취급한다.
5. 중복·충돌·참조 경로를 확인하고 수정 내용을 간결하게 보고한다. 다음 주제도 같은 절차로 진행한다.

사용자가 매번 이 절차를 다시 언급할 필요는 없다. 이 세트의 개정 작업을 이어받는 AI는 먼저 이 절차를 확인한다.

### 주제 순서

1. 공통 함수 설계와 분리 기준
2. React 함수 역할
3. Java 메서드 역할
4. 오류 처리
5. 주석과 문서화
6. 언어별 형식·파일 구조·템플릿
7. 변경·검증 및 참조 조건 조정

각 주제를 핵심 규칙, 짧은 예시, 필요한 예외 순으로 검토한다.
규칙 추가 시 기존 항목과 중복되는지 확인하고, 적용 조건을 함께 적는다.
참고 출처와 채택 판단은 `references/sources.md`에 두며 일반 코딩 시 읽을 필요가 없다.

## 추천 기본값과 변경 가능한 항목

- 보안: 초기 구성·보안 관련 변경에 조건부 적용하며 OWASP·CIS·공급망 보안 기준과 실제 기술 버전의 공식 문서를 참조한다. CI/CD는 도구 공통 기준을 사용하고 제품 문서는 구현 시 보충한다. 기존 프로젝트의 일부 변경에서는 관련 영역만 검토한다.
- 검증: 좁은 검사부터 시작하고 공통 코드·설정 변경 시 확대한다. 같은 상태의 통과 검사는 반복하지 않는다.
- 버전·경고: 프로젝트의 실제 버전·지원 범위에 맞는 문법·API·옵션을 사용하고 변경 부분의 호환성·deprecated 경고를 해결한다. 불필요한 업그레이드·경고 숨김으로 우회하지 않는다.
- 생성 파일·경로: 생성 결과는 원본과 기존 생성 절차로 갱신하고, 개발자 PC의 절대 경로 대신 프로젝트 기준 경로·설정·환경 주입을 사용한다.
- 테스트: 기존 테스트를 우선 활용하고 지속적인 동작·실패·회귀 보호 가치가 있을 때만 추가한다. 단순·중복·커버리지 수치용 테스트를 늘리지 않는다.
- DB 실행: 조회만 기본 허용하며 직접·간접 변경 실행은 대상·작업·영향을 제시하고 명시적 승인 후 수행한다.
- 값 배치: 환경·운영 값은 설정, 빌드 선택은 빌드 설정, 고정 의미는 상수, 제한된 상태·종류는 enum 등으로 표현한다. 기존 정의를 활용하고 공유 의미가 있을 때만 별도 상수 모듈을 만든다.
- 형식 우선순위: 프로젝트 명시 규칙·설정 → 이 세트의 규칙과 언어별 기본 스타일 → 기준이 없는 항목만 주변 관례. 작성·변경 부분에 적용하며 무관한 기존 코드는 재정렬하지 않는다.
- Java 코드 형식: Google Java Style 기반이며 로컬 변경 규칙을 우선한다. 설정이 없으면 4칸·100자. 원문은 로컬에 없는 세부 스타일의 판단이 필요할 때 해당 항목만 확인한다.
- Java·React 공통: 제어 블록·흐름 이탈문 전후를 빈 줄 한 줄로 구분하되 블록 시작·끝은 비우지 않는다.
- React 코드 형식: 설정이 없으면 2칸·100자·작은따옴표·세미콜론·JSX 큰따옴표.
- Java 조회: 새 업무 계약에서 find는 조건 검색, get은 식별자·키 조회로 null 허용, getRequired는 대상 필수로 없으면 업무 예외. 기존 API 계약은 우선한다.
- 문서화: 한국어, 함수 상단 설명과 주요 처리 구간 주석. 설명에는 중요한 데이터 출처·핵심 처리·결과·부수 효과·실패 계약을 포함하며 위임한 핵심 동작도 생략하지 않는다. 단순 함수에 모든 항목을 강제하지 않고 실제 구현과 대조해 검증한다. 작성자·날짜·수정 이력 헤더는 기본으로 생략한다.
- 데이터 변경 안전성: 기존 데이터 보호와 여러 대상 전체의 원자성을 구분한다. 요구사항에 맞게 부분 실패·재실행·복구를 설계하고, 조회 결과 기반 삭제는 범위·권한·완전성을 확인한다. 전체 롤백 체계를 일괄 강제하지 않는다.
- 주석 유지: 기존 소스·쿼리의 의도·배경·제약을 보존하고 변경으로 설명이 달라진 부분만 갱신한다. 이동 시 관련 주석을 함께 옮기며, 일괄 재작성으로 기존 설명을 지우지 않는다.
- 인터페이스: 필요할 때 도입. 프로젝트 관리자가 요구하면 일괄 분리 정책을 따른다.
- TS 모듈: 템플릿은 named export와 type props 예시다. 기존 export·type/interface 관례를 우선한다.
- SQL·MyBatis: 대문자 식별자·4칸·100자·앞쪽 쉼표, SQL 동작 기준 Mapper 이름과 목록의 List 표기, 자동 매핑·별칭 우선. 공통 SQL은 유지보수 이점이 참조 비용보다 클 때만 분리한다.
- UI 스타일: 공통 정의 재사용, 개별 차이만 지정, 역할별 클래스 구조, 현재 작업 범위의 개선을 기본으로 한다. 일반 CSS에 관례가 없으면 BEM을 사용하며, 전체 정리는 명시적 요청 시 진행한다. 유지하는 기존 정의에는 실제 대체 대상·교체 조건을 주석으로 남긴다.
- UI 동작·검증: 목적에 맞는 요소·label·접근 가능한 이름을 사용하고 키보드·포커스를 유지한다. 변경한 화면의 긴 문구·좁은 화면·관련 상태·지원 테마를 확인한다.

이 목록은 사용자 검토용 요약이다. 실제 규칙 원본은 해당 하위 문서이며, 기본값 변경 시 원본과 이 요약을 함께 갱신한다.
