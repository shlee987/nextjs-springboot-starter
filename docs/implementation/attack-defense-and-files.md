# 공격 대응 보완과 파일 업로드 공통 기능

2026-10-30 사용자가 공격 대응·업로드 공통 기능을 함께 정리하고 “이어서 시작해”라고 구현을 승인했다. 기존 UI 개선과 로그 개선은 보존한다. 필터 개수보다 공격이 통과할 수 있는 실제 경계를 점검하고, 이미 안전한 기능은 중복 작성하지 않는다.

## 1. 공격 대응에서 확인·보완할 부분

- SECFILE01: Spring Security의 실제 StrictHttpFirewall 적용과 허용 메서드, 비정상 인코딩·경로·제어문자·헤더 거부를 확인한다. 기본 안전 동작을 완화하지 않는다. 거부 응답도 안전한 오류와 추적 ID를 제공한다. 프록시/컨테이너가 먼저 거부하는 요청은 앱 검증과 구분한다.
- SECFILE02: JSON 중복 키·알 수 없는 필드, 단일 query 중복, 요청 형식·길이·페이지 한도·정렬 허용 목록을 기존 GOV01/02와 대조한다. 필요한 경계에서만 보완한다. 명세된 배열은 허용한다. 예외 원문·요청 본문을 공개하거나 로그에 그대로 넣지 않는다.
- SECFILE03: 모든 MyBatis 사용자 값은 바인딩하고 동적 컬럼/정렬은 코드의 허용 목록을 거친다. SQL 문자열 금칙어 필터를 만들지 않는다. 필드 단위 권한과 리소스 소유권, 요청 DTO의 mass assignment를 확인한다.
- SECFILE04: React 기본 텍스트 출력은 재사용한다. 위험한 HTML 삽입·javascript URL·외부 이동/새 창·DOM 조작 경로를 점검한다. 현재 HTML 편집 기능이 없으면 정제 라이브러리를 추가하지 않는다. 서버 입력 검증과 CSP는 유지한다. 모든 문자열의 태그/따옴표를 지우는 XSS 필터는 만들지 않는다.
- SECFILE05: 공격 예제 검수는 실제 동작 경계와 정상 입력 회귀를 함께 확인한다. SQL 공격 문자열은 값으로 취급되고 스크립트 문자열은 실행되지 않아야 한다. 비정상 경로·중복 필드·권한 없는 파일 접근·파일 형식 위장도 검증한다. WAF/바이러스 탐지 전체 또는 ASVS 전체 준수로 표현하지 않는다.

## 2. 업로드 기본 범위

실제 업로드·내 파일 목록·다운로드·삭제를 제공한다. 검증만 하고 저장하지 않는 가짜 업로드로 완료하지 않는다. 기본 예제는 PNG/JPEG만 허용하고 파일당 5MiB, 한 번에 최대 5개를 선택한다. 서버 요청은 파일 하나씩 보내고 전체 동시 전송 2개로 제한한다. 수치는 이 예제의 기본값이며 공식 보안 표준의 수치가 아니다. PDF/Office/SVG/HTML/압축파일과 URL에서 가져오기는 이번 범위에서 제외하고 필요 조건을 설명한다.

- SECFILE06: 공통 FileUpload 컨트롤은 선택·드래그앤드롭·키보드·개수/크기/형식 안내·선택 제거·실제 전송 진행률·취소·실패 재시도를 제공한다. 선택 상태와 서버에 저장 완료된 상태를 구분한다. 100% 전송이 서버 저장 완료를 뜻하지 않으며 처리 중 상태를 따로 보여준다. 취소가 서버 저장 취소/삭제를 보장한다고 표시하지 않는다. 이미지 미리보기 object URL은 정리한다. 서버 오류를 공통 안전 메시지로 표시한다.
- SECFILE07: 서버는 인증·CSRF·Origin·요청 제한을 유지하고 확장자/전달 MIME/실제 내용 검사를 조합한다. 클라이언트 accept와 검증은 사용자 안내이며 보안 경계가 아니다. 작은 시그니처 검사만으로 안전한 이미지라고 판단하지 않는다. 크기 제한 뒤 디코딩 전에 폭/높이/픽셀 상한(각 8192px, 총 16M 픽셀)을 검사하고 정상 디코딩·재인코딩한 이미지 바이트를 저장한다. 원본 메타데이터는 제거한다. 자원 사용은 제한하며 실제 JDK 이미지 구현과 지원 형식을 확인한다.
- SECFILE08: 저장소 인터페이스와 로컬 디스크 구현을 분리한다. local은 Git 추적되지 않는 전용 경로, 공유 환경은 외부 저장 루트 주입을 요구한다. 웹 정적 공개 폴더에는 저장하지 않는다. 생성한 식별자/저장 키만 파일 경로에 사용하고 원본 파일명은 제한된 표시 메타데이터로만 사용한다. 경로 탈출·절대 경로·심볼릭 링크·덮어쓰기·제어문자/헤더 삽입을 막는다. API로 서버 경로를 받거나 노출하지 않는다. 클라우드 SDK를 미리 설치하지 않는다. 로컬 디스크는 멀티서버 공유 저장소를 보장하지 않는다고 설명한다.
- SECFILE09: 파일 메타데이터는 DB/Flyway/MyBatis로 관리한다. 기존 대문자 언더바·UTC/밀리초·문자열 ID 계약을 따른다. 사용자별 목록/권한을 확인하고 불투명 파일 ID만으로 접근을 허용하지 않는다. 기본은 소유자만 접근하며 관리자의 무조건 우회는 만들지 않는다. 다운로드는 attachment·안전한 파일명·nosniff/no-store를 적용한다. 파일명·내용을 감사 로그에 그대로 넣지 않는다.
- SECFILE10: DB와 디스크가 하나의 트랜잭션이라고 가정하지 않는다. 임시 저장→검증/재인코딩→최종 저장/메타데이터 공개의 실패·정리 경계를 설계한다. 다운로드는 완료 상태만 허용한다. 삭제 실패를 성공으로 가장하지 않으며 무분별한 자동 디렉터리 삭제를 하지 않는다. 소유자당 저장 한도 기본 100MiB를 동시성까지 고려해 강제하고 잘못된 요청은 용량을 소비하지 않게 한다. 업로드 횟수와 전체 동시 이미지 처리 상한을 두고 대기열은 무한히 늘리지 않는다.

현재 공통 요청 본문 제한과 multipart 컨테이너/Next 프록시 제한을 함께 확인한다. 일반 JSON 본문 제한을 전역으로 키우지 않고 정확한 업로드 메서드/경로만 5MiB+제한된 multipart 여유 크기를 허용한다. Content-Length 없는 스트리밍 요청도 제한한다. 경로만 보고 인증 전 multipart를 무제한 읽지 않는다. 파일형식 검사가 악성코드 전체 탐지를 보장하지는 않는다. 바이러스 검사/CDR는 확장 지점과 미도입 한계를 명시하고 성공을 가장하는 가짜 검사기를 추가하지 않는다.

## 3. API 경계와 예제

백엔드가 소유하는 OpenAPI 출력으로 다음 경로와 실제 스키마를 먼저 전달한다: GET/POST /api/files, GET /api/files/{fileId}/content, DELETE /api/files/{fileId}. 업로드는 multipart field file 1개, 목록은 기존 페이지 계약, 오류는 기존 공통 계약. 다운로드 바이트와 응답 헤더·삭제의 HTTP 상태를 명시한다. 실제 spec은 설계 담당이 검증해 docs/api/openapi.json에 반영하고 프론트가 Orval을 생성한다. 스키마를 추측해 가짜 생성물로 실연동 완료를 주장하지 않는다.

프론트는 기존 예제 메뉴 안에 파일 업로드 예제를 추가해 정상 업로드/목록/다운로드/삭제와 안전한 오류를 쉽게 확인하게 한다. 업로드 버튼은 기존 UIOPT09 중복 실행 방지와 연결한다. 백엔드가 준비되기 전까지 공통 UI·진행 상태·검증 예제는 구현 가능하지만 실연동 상태는 대기로 표시한다.

## 4. 작업·검수·실행 범위

backend/**는 백엔드, frontend/**는 프론트, docs/**는 설계 담당이 관리한다. 새 채팅/모델/추가 subagent·커밋/push·기존 서버 교체는 하지 않는다. 필요한 라이브러리는 기존 도구/JDK로 해결 가능한지 먼저 확인한다. 불필요한 정제/백신/스토리지 패키지를 설치하지 않는다.

기존 로컬 검증 승인 대상과 새 파일 테이블 migration/디스크 저장의 실제 실행은 구분한다. 우선 코드·SQL·DB 없는 시험을 완료하고 백엔드가 새 테이블 적용 대상DB/명령/파일저장루트/용량/정리·복구 영향을 비공개 실행계획으로 전달한다. 기존 검증 범위에 포함되는지 조정자가 대조한 뒤 필요한 실행만 확정한다. 승인 대기 때문에 구현과 독립 리뷰를 중단하지 않는다. 기존 DB/Redis0/컨테이너/사용자 서버를 초기화하지 않는다.

완료에는 공격 입력과 정상 회귀, 이미지 위장/크기/픽셀 제한, 다른 사용자 접근 거부, 동시 업로드 한도, DB/디스크 실패 후 노출·정리, 다운로드 헤더, 실제 PC/모바일 업로드 상태와 키보드 확인을 구분한다. 기존 로그 개선 및 공통 컨트롤 수정도 보존하고 함께 회귀 확인한다.

## SECFILE11 — 업로드 화면 디자인 보완 (2026-10-30 사용자 추가 요청)

사용자가 현재 업로드 예제 스크린샷을 보고 디자인 적용을 요청했다. 기능 검수와 별개로 아래 시각 기준을 반영한다.

- 기본 브라우저 file input의 회색 버튼/파일명 표시는 화면에 노출하지 않는다. 접근 가능한 실제 input은 유지하고 기존 공통 Button과 label/ref 등으로 연결한다. 마우스·키보드로 파일 대화상자를 열 수 있어야 하며 임의의 div 클릭만 제공하지 않는다.
- 드롭 영역은 밝은 배경·정돈된 점선 테두리·업로드 아이콘·짧은 제목·보조 문구·파일 선택 버튼으로 구성한다. “이미지를 끌어 놓거나 파일을 선택하세요”처럼 행동을 먼저 설명한다. 파일 형식/용량/개수는 보조 정보로 계층을 낮춘다. hover/drag-over/focus/disabled/error 상태를 구분한다.
- 선택 후에는 썸네일·파일명·크기·상태·삭제/취소/재시도를 정렬된 파일 행/카드로 표시한다. 진행률은 기존 토큰과 색을 공유한다. 긴 파일명은 레이아웃을 밀지 않으며 필요한 경우 전체 이름을 확인할 수 있다.
- 업로드 버튼은 파일 개수/선택 요약과 함께 명확한 작업 구역에 배치한다. 대기/선택/검증실패/전송중/서버처리중/완료/실패 상태에서 간격·버튼중앙·대비·폭을 확인한다.
- 현재 API 연결 대기는 작은 상태 안내 영역으로 정돈하고 완료로 가장하지 않는다. 개발 구현 설명은 접힌 사용 코드/개발 안내로 옮기고, 사용자 영역에는 “파일 업로드는 준비 중이에요. 지금은 파일을 선택해 확인할 수 있어요.”처럼 실제 가능한 행동을 설명한다. 취소 한계 등 필수 설명은 짧게 나누고 긴 한 줄로 넘치지 않게 한다.
- PC에서는 지나치게 큰 빈 영역을 줄이고 선택 파일 목록·액션을 읽기 쉽게 배치한다. 모바일은 적절히 줄바꿈하고 가로 넘침 없이 조작할 수 있게 한다. 기존 파일 보안/전송/접근성 기능을 스타일 작업으로 제거하지 않는다.
- 빈 상태뿐 아니라 실제 파일 선택·오류·진행 상태와 PC/모바일을 직접 시각 검수한다. 추측으로 완료하지 않는다. 새 UI 프레임워크/아이콘 라이브러리 설치는 필요 없다.

### 로컬 저장 위치의 수명

기본 이미지 저장 루트는 Git 무시된 전용 디렉터리이며 build/임시 빌드 폴더 밖에 둔다. Gradle clean으로 실제 이미지가 삭제되고 DB 메타데이터만 남지 않아야 한다. 루트 변경 시 기존 저장 파일을 자동 이동·삭제하지 않는다. 상대 경로의 기준 작업 디렉터리는 백엔드 실행 안내에서 명시하고, 검증에서는 별도 APP_FILES_ROOT를 주입한다.


### 인증 경계와 파일 화면 상태의 수명

사용자 세대가 바뀔 때 인증 Guard까지 세대 key로 재마운트하지 않는다. 인증 확인이 실패할 때 세대 변경과 Guard 재마운트가 맞물리면 익명 요청이 반복될 수 있다. 인증 경계는 유지하고 파일 선택·미리보기·페이지·Query 캐시만 새 사용자 범위로 초기화한다. 늦게 끝난 이전 업로드는 새 목록을 갱신하지 않고, 이전 다운로드는 저장을 시작하지 않는다. 초기 익명 진입과 실제 로그인→로그아웃→재로그인 전환을 각각 확인하며, 로그아웃 뒤 요청 수가 더 증가하지 않고 이전 파일·선택·미리보기가 없어야 한다.
