# 설명 문구와 로컬 로그 개선

2026-10-29 사용자가 진행 중인 UI 정리에 추가한 요구사항이다. 사용자는 이번 추가 작업도 담당자에게 전달해 진행하도록 승인했다.

## 1. 설명은 사용자가 바로 이해할 수 있게 쓴다

화면과 안내 문서는 짧고 자연스러운 한국어로 쓴다. 기술적으로 정확한 내용은 유지하되, 처음 읽는 사람이 무엇을 해야 하는지부터 알려준다.

- 제목은 기능의 목적을 말한다. 예를 들어 “RHF + Zod 폼”보다 “입력 검증과 제출”을 먼저 쓴다. 라이브러리 이름은 보조 설명이나 코드에서 소개한다.
- 문장은 주어와 서술어를 갖춘다. 띄어쓰기 없이 코드·조건·명사를 이어 붙인 설명을 만들지 않는다.
- “계약”, “소유”, “경계”, “합성”, “진입”, “허용목록” 같은 표현은 꼭 필요한 설계 설명에서만 쓴다. 일반 안내에서는 “기준”, “관리하는 곳”, “적용 범위”, “테스트용”, “시작”, “허용한 항목”처럼 이해하기 쉬운 말을 고른다.
- 먼저 용도, 다음에 사용 방법, 마지막에 주의점을 설명한다. 내부 설정과 검증 이력을 화면의 주된 설명에 넣지 않는다.
- 예제에는 해볼 동작과 예상 결과를 함께 적는다. 실제 저장하지 않는 예제는 “화면에서 동작을 확인하는 예제입니다. 서버에 저장하지 않습니다.” 정도로 안내한다.
- 코드·API·환경변수·오류 코드·필수 조건의 의미를 바꾸지 않는다. “해야 한다/할 수 있다/아직 확인하지 않았다”의 차이는 유지한다.
- 과거 기록은 현재 결과와 구분한다. 예전의 “통합 시험 대기”를 실제 연결이 끝난 화면에 그대로 보여주지 않는다.

예시:

| 기존 표현 | 바꿀 표현 |
| --- | --- |
| 합성 제출 실패 | 제출 실패 재현 |
| 실패 입력 유지·진행 중 중복 제출 | 제출에 실패해도 입력한 내용은 남습니다. 처리 중에는 다시 제출할 수 없습니다. |
| 실제 API/인증 통합 검증은 준비·승인 후 수행 | 로그인하면 실제 서버에서 정보를 불러옵니다. 테스트 데이터만 사용하세요. |
| 결과는 담당 문서가 소유 | 자세한 결과는 검증 기록에서 확인할 수 있습니다. |

frontend의 화면·예제·README·FEATURES·변경 이력은 프론트 담당자가, backend의 README·VERIFICATION·변경 이력은 백엔드 담당자가 정리한다. 루트와 docs/implementation은 설계 담당자가 정리한다. 코드/이름/과거 증거를 일괄 치환하거나 검증 상태를 좋게 보이도록 바꾸지 않는다.

## 2. 로컬 콘솔은 기동 상태와 로그 종류가 잘 보여야 한다

지금은 시작 배너와 기동 정보가 꺼져 있고, 외부 라이브러리 메시지를 모두 framework_event로 바꾸고 있다. 로그를 숨기는 데 치우쳐 개발자가 원인과 상태를 파악하기 어렵다. 다음 기준으로 고친다.

- local에서 Spring Boot 기본 시작 배너를 다시 보여준다. 기동을 시작한 상태와 준비가 끝난 상태를 구분한다. 배너가 보였다는 이유만으로 준비 완료를 표시하지 않는다.
- 서버의 필수 설정·DB/Redis·인증 준비가 성공한 뒤에 준비 완료 로그를 한 번 남긴다. 앱 이름, 환경, 실제 포트, 걸린 시간처럼 개발자가 필요한 정보를 보여준다. 실패한 앱에는 준비 완료가 나오면 안 된다.
- 시간은 기존 UTC 밀리초 형식을 유지한다. 레벨·분류·짧은 logger·메시지를 구분하고, 요청 안에서만 traceId와 사용자 정보를 표시한다. 값 없는 traceId= actorUserId= 항목을 모든 줄에 반복하지 않는다.
- 색상을 지원하는 콘솔에서는 레벨과 분류에 색을 쓴다. 색을 끄거나 지원하지 않는 경우에도 [READY], [HTTP], [SQL], [ERROR] 같은 표시만으로 읽을 수 있어야 한다. ANSI를 항상 강제로 켜지 않는다.
- 프레임워크의 실제 시작·종료·연결 상태를 확인할 수 있게 한다. 모든 외부 로그를 무의미한 한 단어로 바꾸지 않는다. 필요한 메시지는 안전하게 가공해 보여주고, 비밀이 섞일 수 있는 설정 덤프·HTTP 본문·토큰·원문 SQL 예외는 열지 않는다.
- 오류는 안전한 요약과 원인 종류, 확인할 코드 위치를 읽기 쉬운 여러 줄로 보여준다. 중첩 예외와 긴 logger를 공백 없이 이어 붙이지 않는다. API 응답에는 기존처럼 실제 예외와 내부 정보를 보내지 않는다.
- root INFO를 유지한다. SQL을 보기 위해 전체 로그를 DEBUG로 바꾸지 않는다. 같은 요청이나 오류가 여러 번 중복 출력되는지도 확인한다.

표시 형태의 예시다. 아래 값은 설명용이며 실제 성공 기록이 아니다.

```text
2026-10-29 07:00:00.000 INFO  [START] starter-api — local 환경에서 시작합니다.
2026-10-29 07:00:03.250 INFO  [READY] starter-api — 포트 18080, 준비 완료 (3.25초)
2026-10-29 07:00:05.120 INFO  [HTTP] GET /api/departments → 200 (18ms) [trace=…]
2026-10-29 07:00:05.118 DEBUG [SQL] DepartmentMapper.selectList (4ms, SUCCESS)
  SQL:
    SELECT ...
    LIMIT ? OFFSET ?
  PARAMS:
    page.size = 20
    page.offset = 0
```

## 3. SQL과 파라미터를 함께 읽을 수 있게 한다

이 절은 backend-observability의 기존 SQL01에서 파라미터를 전부 숨기던 로컬 정책을 대체한다. 다른 환경의 상세 SQL 금지와 민감정보 보호는 유지한다.

- 기존 MyBatis 진단 기능을 확장한다. 실행에 사용한 BoundSql과 ParameterMapping에서 실제 순서·속성·타입을 읽고, SQL과 파라미터를 구분된 블록으로 보여준다. 단순 Map 출력이나 객체 전체 toString을 쓰지 않는다.
- 우선 SQL + 이름/타입/가공된 값의 PARAMS 형식으로 파라미터를 추적할 수 있게 한다. 실행값을 반영한 보기용 SQL을 제공한다면 문자열·주석·달러 인용·물음표 연산자와 값의 따옴표 처리를 정확히 지원해야 한다. 물음표를 정규식으로 순서대로 치환하는 구현은 금지한다. 정확성을 보장하기 어렵다면 PARAMS 방식으로 충분히 읽을 수 있게 하고 한계를 설명한다.
- 페이징 숫자, 내부 식별자, 서버가 검증한 상태/종류 코드, 날짜 범위처럼 진단에 필요한 값은 명시적으로 허용한다. 검색어·이름·이메일·로그인 ID 등 개인정보와 비밀번호·해시·JWT·refresh·쿠키·키·DB 자격은 기본으로 가린다. 허용하지 않은 속성은 타입과 [MASKED]만 표시한다. 이름에 password가 없다는 이유만으로 임의 문자열을 출력하지 않는다.
- 민감값은 로그 문자열을 만들기 전에 가린다. 인증/자격/개발키 SQL은 기존처럼 상세 SQL과 파라미터를 모두 생략하고 Mapper와 시간·결과만 보여준다. 예외 원문과 조회 결과 행은 출력하지 않는다.
- null, 단일 값, DTO/Map, foreach 추가 파라미터, 시간/숫자, 긴 문자열, 제어문자와 바이너리/스트림을 안전하게 처리한다. 로깅 때문에 스트림을 소비하거나 실제 파라미터·실행 SQL·타입핸들러 동작을 바꾸지 않는다.
- 전체/필드별 출력 길이와 개수를 제한한다. SQL 줄바꿈은 유지하고 파라미터의 CR/LF·ANSI 제어문자는 이스케이프한다. 로그에 가짜 레벨/완료 표시를 넣을 수 없어야 한다.
- local에만 적용한다. dev/stg/prod는 상세 SQL/파라미터 출력 없이 기존 JSON 파일과 오류 분리를 유지한다. 공개 문서에는 합성 값의 짧은 예시만 넣는다.

## 4. 확인할 내용

백엔드는 변경 전후의 로컬 콘솔 예시를 준비하고, 배너·시작·성공 준비 완료·실패 구분, 색상 켜짐/꺼짐, Mapper별 SQL/파라미터 순서, foreach/null/민감표식/제어문자, 같은 연결/트랜잭션 불변과 공유 환경 미출력을 검사한다. 로그인·CSRF·오류 비노출 등 기존 회귀도 유지한다. 새로운 로깅 제품이나 테스트 플랫폼을 기본 설치하지 않는다.

현재 사용 중인 서버는 임의 종료하지 않는다. 검증은 별도 실행 사본과 포트에서 하고, 사용자에게 보여줄 실행본 반영은 본인이 만든 프로세스인지 확인한 뒤 조정한다. DB/Redis 초기화·정책 변경·마이그레이션·비밀번호 변경·커밋/push는 이번 추가 요구사항에 포함하지 않는다. 기존 승인된 로컬 합성 환경은 필요한 읽기/인증 회귀에만 사용한다.
