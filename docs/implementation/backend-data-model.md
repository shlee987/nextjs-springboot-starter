# 공통 DB 모델과 Flyway 설계

기준일: 2026-10-30 / 상태: 공통 사용자·권한·인증·감사 DDL과 seed는 격리 로컬 DB에서 적용·검증했다. 추가 파일 테이블은 [파일 설계](attack-defense-and-files.md)와 최신 [검증표](../../backend/VERIFICATION.md)를 따른다. [전체 범위](backend-foundation.md), [인증](authentication-foundation.md), [이력](backend-observability.md)을 적용한다.

## 1. 이름·타입·기본 제약

- PostgreSQL18, 업무 schema public. 테이블·컬럼·제약·인덱스 실제 이름은 대문자 언더바, 큰따옴표로 참조. schema 및 Flyway history는 기존 프레임워크 이름 유지. 객체명은63byte 이하.
- PK bigint GENERATED BY DEFAULT AS IDENTITY, API ID 문자열. 내부 로그인/이력 식별자 UUID는 문자열 API. 인증 token은 식별자와 다르고 원문 공개 금지.
- 코드 varchar(64), 상태 varchar(16) CHECK 허용값, 이름 varchar(100), 메시지/사유는 코드로 제한. 사용자 입력 무제한 text 금지.
- 시점 timestamptz(3), UTC. 시간 값은 공통 Clock에서 밀리초로 절삭하고 바인딩. 날짜 date. 큰 정밀 수량은 NUMERIC(p,s) 업무별 지정, double 금지.
- 아래 ?는 NULL 허용, 생략하면 NOT NULL. FK가 있는 컬럼은 대상 PK 타입 일치, FK 조회 인덱스 명시. 암묵 cascade로 업무/이력 삭제 금지.
- M = CREATED_AT, CREATED_BY?, UPDATED_AT, UPDATED_BY?, VERSION(bigint default0). BY는 내부 userId이며 시스템/초기 seed는 null, 이력 보존을 위해 BY에 FK 강제하지 않음. VERSION은 변경 시 조건 update +1, 영향0은409.
- USER/ROLE 등 기준 데이터는 물리 삭제 API 미제공, 비활성화. 연결 테이블은 명시 서비스 트랜잭션으로 관리. 개인정보 파기/실제 탈퇴는 후속 별도 정책.

## 2. 사용자·조직·권한 (기본 구성)

| 테이블 | 컬럼·제약 |
| --- | --- |
| APP_USER | USER_ID PK, LOGIN_ID varchar(50) UNIQUE, DISPLAY_NAME varchar(100), EMAIL varchar(254)?, STATUS ACTIVE/INACTIVE, M. LOGIN_ID 정규식 CHECK |
| LOCAL_CREDENTIAL | USER_ID PK/FK APP_USER, PASSWORD_HASH varchar(512), PASSWORD_CHANGED_AT. 비밀번호/과거해시 평문 컬럼 없음 |
| EXTERNAL_IDENTITY | IDENTITY_ID PK, USER_ID FK, PROVIDER_CODE varchar(64), ISSUER varchar(512), SUBJECT varchar(255), CREATED_AT, UNIQUE(PROVIDER_CODE,ISSUER,SUBJECT). 외부 연결 경계만 제공, 가짜 IdP행 없음 |
| DEPARTMENT | DEPARTMENT_ID PK, DEPARTMENT_CODE UNIQUE, DEPARTMENT_NAME, PARENT_ID? FK self, SORT_ORDER int default0 CHECK>=0, ACTIVE boolean defaulttrue, M |
| USER_DEPARTMENT | USER_ID/DEPARTMENT_ID 복합PK·FK, IS_PRIMARY boolean, CREATED_AT/BY?. USER_ID WHERE IS_PRIMARY=true 부분 UNIQUE |
| APP_ROLE | ROLE_ID PK, ROLE_CODE UNIQUE, ROLE_NAME, ACTIVE boolean, M |
| APP_PERMISSION | PERMISSION_ID PK, PERMISSION_CODE UNIQUE, PERMISSION_NAME, CREATED_AT. 코드 추가는 버전 SQL/코드 배포 |
| USER_ROLE | USER_ID/ROLE_ID 복합PK·FK, CREATED_AT/BY? |
| ROLE_PERMISSION | ROLE_ID/PERMISSION_ID 복합PK·FK, CREATED_AT/BY? |

DEPARTMENT 자기참조 CHECK(PARENT_ID<>DEPARTMENT_ID)는 직접 순환만 막으므로, 부서 변경 서비스에서 조상 탐색·변경 잠금으로 간접 순환도 차단한다. ACTIVE=false 부서에 신규 소속 부여 금지. 대표 부서는 실제 소속이어야 함. 사용자가 없을 때 default 부서/권한을 임의 생성하지 않는다.

필수 인덱스: APP_USER(STATUS,USER_ID), USER_DEPARTMENT(DEPARTMENT_ID,USER_ID), DEPARTMENT(PARENT_ID,SORT_ORDER,DEPARTMENT_ID), USER_ROLE(ROLE_ID,USER_ID), ROLE_PERMISSION(PERMISSION_ID,ROLE_ID). 사용자/부서 목록 기본정렬 ID ASC, 추가정렬 displayName/departmentName은 허용 enum과 ID tie-breaker. 같은 소속/역할 중복은 UNIQUE로 거부.

## 3. 토큰 인증 상태 (JDBC 모드만)

이 테이블은 Spring Session과 별개다. Redis 모드에는 생성하지 않는다. 사용자 테이블에는 토큰 버전 컬럼을 추가하지 않는다.

| 테이블 | 컬럼·제약 |
| --- | --- |
| AUTH_USER_GUARD | USER_ID bigint PK(FK 없음), BLOCKED boolean defaultfalse, OPERATION_ID uuid?, UPDATED_AT. 사용자별 잠금 행, 계정 정리와 독립 |
| AUTH_LOGIN | LOGIN_ID uuid PK(sid), USER_ID bigint, CREATED_AT, AUTHENTICATED_AT, LAST_ACTIVITY_AT, IDLE_EXPIRES_AT, ABSOLUTE_EXPIRES_AT, REVOKED_AT?, REVOKE_REASON varchar(64)?, CURRENT_REFRESH_HASH char(64) UNIQUE, PERMISSIONS_JSON jsonb(문자열배열 CHECK). USER_ID FK 없음 |
| AUTH_REFRESH_HISTORY | TOKEN_HASH char(64) PK, LOGIN_ID uuid FK AUTH_LOGIN ON DELETE CASCADE, USED_AT, EXPIRES_AT. 사용된 해시만, 원문 없음 |
| AUTH_ATTEMPT_BUCKET | BUCKET_TYPE ACCOUNT/IP/REQUEST, BUCKET_KEY char(64), WINDOW_START_AT, ATTEMPTS int CHECK>=0, BLOCKED_UNTIL?, EXPIRES_AT. PK(TYPE,KEY,WINDOW_START_AT) |

인덱스 AUTH_LOGIN(USER_ID,ABSOLUTE_EXPIRES_AT), AUTH_LOGIN(IDLE_EXPIRES_AT), AUTH_REFRESH_HISTORY(EXPIRES_AT), AUTH_ATTEMPT_BUCKET(EXPIRES_AT). 로그인 히스토리는 조회 감사가 아니라 유효성 상태이며 감사 데이터 대체 금지.

만료 job은60초 간격 최대1000건씩 만료 AUTH_LOGIN(절대 만료/폐기 포함)·bucket 정리, 여러 서버는 SKIP LOCKED/조건 삭제로 중복 안전. 폐기 sid/사용된 refresh 해시는 절대 만료까지 tombstone 유지. 토큰 만료 이전에 정리해서 미사용 hash를 정상 토큰으로 오인하지 않는다. guard는 자동 전체 purge 금지, 사용자 수 범위의 잠금 행만 유지.

Redis는 같은 모델을 app/env prefix와 user hash tag 아래 저장, TTL은 절대 만료와 남은 수명 기준. 인덱스 정리와 token locator 제거를 함께 처리하고 누락은 인증 실패. 데이터가 없는 상태에서 자동 로그인 복원 금지.

## 4. Spring Session 테이블 (JDBC + prelogin enabled만)

별도 schema auth_session을 두고 실제 테이블은 "SPRING_SESSION", "SPRING_SESSION_ATTRIBUTES". 두 테이블 사이의 내부 FK만 허용하고 업무·토큰 테이블과 FK를 연결하지 않는다. 패키지 기본 PostgreSQL DDL을 그대로 중복 실행하지 말고 설치된4.1.1의 구조를 기준으로 큰따옴표·schema를 적용한다.

- 본체: PRIMARY_ID char(36) PK, SESSION_ID char(36) UNIQUE, CREATION_TIME bigint, LAST_ACCESS_TIME bigint, MAX_INACTIVE_INTERVAL int, EXPIRY_TIME bigint, PRINCIPAL_NAME varchar(100)?. 프레임워크 epoch 단위 유지.
- 속성: SESSION_PRIMARY_ID char(36) FK 본체 ON DELETE CASCADE, ATTRIBUTE_NAME varchar(200), ATTRIBUTE_BYTES bytea, 복합PK(SESSION_PRIMARY_ID,ATTRIBUTE_NAME).
- EXPIRY_TIME/PRINCIPAL_NAME 인덱스. bytea 내용은 allowlist JSON converter로 명시, native Java serialization 금지.
- JdbcIndexedSessionRepository 기본 SQL은 따옴표 없는 uppercase를 PostgreSQL이 소문자로 바꿀 수 있다. tableName만 바꾸면 충분하다고 가정하지 말고 CRUD/findByIndex/cleanup의 사용자 SQL 전부를 schema와 quoted column으로 맞추고 왕복 시험한다.
- Spring Session 초기화는 initialize-schema=never. 기본 정리 기능은60초 기준으로 제한, 토큰 상태 job과 별개. session enabled=false면 SQL·listener·cleanup 접근 자체가 없어야 함.

## 5. 접근·보안 이력 (기본 구성)

| 테이블 | 컬럼·제약 |
| --- | --- |
| ACCESS_AUDIT | AUDIT_ID uuid PK(동일 이벤트 중복 방지), OCCURRED_AT, ACTOR_USER_ID bigint?, ACTOR_KIND USER/ANONYMOUS/SYSTEM, RESOURCE_CODE varchar(64), ACTION_CODE varchar(32), TARGET_TYPE varchar(64)?, TARGET_ID varchar(128)?, OUTCOME STARTED/SUCCESS/FAILURE/DENIED/UNKNOWN, REASON_CODE varchar(64)?, TRACE_ID uuid, SERVER_ID varchar(100), CLIENT_IP inet?, USER_AGENT varchar(256)?, OPERATION_ID uuid?. append-only |
| SECURITY_AUDIT | EVENT_ID uuid PK, OCCURRED_AT, EVENT_CODE varchar(64), ACTOR_USER_ID bigint?, TARGET_USER_ID bigint?, OUTCOME SUCCESS/FAILURE/DENIED/UNKNOWN, REASON_CODE?, TRACE_ID uuid, SERVER_ID, CLIENT_IP inet?, LOGIN_REFERENCE char(64)?. append-only |

로그인 reference는 raw sid 대신 로그 전용 HMAC 지문, 키는 외부 관리(local은 개발키에서 별도 파생 용도/label 적용). 실제 세션/refresh/access 원문 저장 금지. FK를 사용자에 걸어 삭제에 따라 이력이 사라지지 않게 한다. 필요하지 않은 PII/브라우저 정보는 수집하지 않으며 CLIENT_IP는 개인정보 취급·접근 제한 대상이다.

인덱스 각 테이블(OCCURRED_AT,AUDIT_ID/EVENT_ID), (ACTOR_USER_ID,OCCURRED_AT), ACCESS(RESOURCE_CODE,OCCURRED_AT), SECURITY(TARGET_USER_ID,OCCURRED_AT). traceId 조회 인덱스도 둔다. TARGET_ID는 마스킹된 표시명 대신 승인된 내부ID, 검색어/응답/변경값 JSON 컬럼 없음.

공유 환경 runtime 계정은 감사 테이블 SELECT/INSERT만, UPDATE/DELETE 금지. 업무 변경과 함께 쓰는 SECURITY_AUDIT도 INSERT-only. 별도 보존 관리 계정만 명시 삭제, local testuser 단일 권한은 편의 예외. 이력 조회 API 자체도 ACCESS_AUDIT 대상이며 재귀 호출 없이 low-level writer를 사용한다.

## 6. local 키와 합성 초기 데이터

- schema starter_local_only의 "DEV_SIGNING_KEY": KEY_ID varchar(64) PK, PRIVATE_KEY_PKCS8 bytea, PUBLIC_KEY_SPKI bytea, CREATED_AT, ACTIVE boolean(활성1개 부분UNIQUE). local에서만 연결·생성·사용, 공개 migration에 개인키 literal 없음.
- local 최초 시작 시 PostgreSQL transaction advisory lock으로 RSA3072 키 생성/기존 조회를 직렬화. 여러 노드가 같은 DB의 동일 키 사용. 평문 개발키 저장은 local loopback 공개 테스트 DB 전용 편의이며 dev/stg/prod는 이 schema 참조 자체 금지. JAR에 키를 빌드하지 않음.
- 합성 계정 localuser / localadmin, 비밀번호 LocalExample1234! (공개 예제, 실환경 사용 금지), Argon2id hash만 seed SQL에 저장. 사용자는 USER/ADMIN 역할, 부서 DEMO. ID는 고정 합성 범위로 관리하고 identity 시퀀스가 충돌하지 않도록 보정.
- shared env에는 위 schema/seed 없음. 최초 관리자 생성은 운영 담당자가 승인된 비밀 입력으로 실행하는 별도 절차(명령 인자·로그에 원문 금지). MFA/운영 보존 정책이 미확정이면 관리자 외부 공개 보류.

## 7. Flyway 소유와 제거 절차

| 경로 | 실행 조건·history |
| --- | --- |
| db/migration/core | 모든 모드: 사용자/조직/권한/감사. public.flyway_schema_history 기존 연속 버전 |
| db/migration/auth-jdbc | state-store=jdbc: 인증 상태. public.auth_jdbc_schema_history 독립 |
| db/migration/session-jdbc | jdbc+prelogin=true: auth_session 전용. auth_session.flyway_schema_history 독립 |
| db/migration/local | local: 합성 seed·개발키 schema. public.local_seed_schema_history 독립 |

기존 빈 db/migration 루트에 중첩 폴더를 추가하면 Flyway 재귀 검색으로 선택 migration까지 실행될 수 있다. 공통 migration 위치를 core로 명시 변경하고 루트를 함께 넣지 않는다. 1차 적용된 history는 보존하고 다음 버전부터 연결한다. 독립 runner 네 개의 조건·순서(core→선택auth→선택session→local)·schema create·실행권한을 문서화한다. 앱 core runner와 자동 Boot runner가 같은 SQL을 이중 실행하지 않게 한 경로만 소유.

local은 승인된 실행에서 자동 적용. dev/stg/prod는 앱 자동 migration=false, 별도 migration runner/명령으로 적용, 업무 runtime의 CREATE 권한 금지. Flyway clean 자동 실행·baseline-on-migrate로 기존 DB 덮기·이미 적용된 SQL 수정 금지. 신규 설치/재시작/버전 변경 시 데이터 유지 시험.

JDBC 임시 세션 제거: 모든 노드에서 prelogin=false·진행 로그인 종료 → 백업/실제 대상 확인 → 승인된 별도 제거 SQL로 auth_session의 본체/속성/전용 history 제거. 다음 시작이 schema를 참조/재생성하지 않는지 확인. 이후 다시 켜면 전용 신규 migration으로 빈 세션 생성·재로그인. core/토큰/사용자 이력은 영향 없음.

토큰 상태 JDBC는 임시 세션을 제거해도 유지한다. state-store 전환 시 기존 토큰 상태를 이관하지 않고 폐기하며 옵션 테이블 삭제는 별도 승인한다. 소스 migration 파일을 지우거나 공통 history를 삭제하는 것으로 전환하지 않는다.

## 파일 메타데이터 확장 (2026-10-30)

파일 기능은 core의 새 V2 migration으로 FILE_OWNER_QUOTA와 FILE_ASSET을 추가한다. 소유자·저장 키·표시 이름·형식·재인코딩 크기·폭/높이·생성시각·상태를 관리한다. 예약/삭제 중 용량도 소유자 한도에 포함하고 READY 상태만 목록·다운로드로 공개한다. 기존 migration을 수정하지 않는다. 상세 실패/정리 기준은 [파일 설계](attack-defense-and-files.md), 실제 적용 여부는 [백엔드 검증표](../../backend/VERIFICATION.md)를 따른다.
